# 攻击维度清单

从真实交付案例的反模式表提炼。用途：① 构造 opposition brief 时摘取分配给各 reviewer 的维度；② 主会话自查规约时逐维度过一遍。每条以"攻击问句"给出——对着规约问，答不上来就是问题。

## 1. 边界误伤（token / 前缀 / 模式匹配）

- 规约中的任何"查找替换 / 匹配 / 过滤"操作，是否会误伤共享前缀的相邻标识符？（例：替换 `$pay_money` 的 naive regex 会连 `$pay_money_deliver` / `$pay_money_origin` 一起换掉）
- 匹配规则有没有声明边界语义（token 边界 / 单词边界 / 精确全等）？还是默认"应该不会撞"？
- 有没有列出**不应被命中**的相似目标清单，并写进测试？

## 2. 作用域与隔离（chain / scope）

- 操作的生效范围是否显式限定？同一载体里"命中段 + 非命中段"混排时（如一条公式里多个 action_type 拼接），是否只改命中段？
- 有没有"天然排除"的依赖假设（例：某类目标挂在非白名单分支上所以不用处理）？这个假设有证据吗，还是碰巧成立？
- 配置/数据变更的影响面清单是 grep 实证得来的，还是"我以为只有这几处"？

## 3. 验收标准可靠性

- 验收标准是否依赖"数值变大/变小/不同"这类环境敏感断言？（数据可能为空、负值、恰好持平——"变大"不可靠）
- 能否换成确定性断言：expression/output snapshot + mock 输入下的精确期望值？
- 验收步骤能否由第三方照着执行并得到同一结论？还是只有作者知道"看哪里"？

## 4. 变换后校验（parse / validate / fallback）

- 任何字符串级/结构级变换（替换、拼接、生成），变换产物有没有 parse/schema 校验步骤？
- 校验失败时的 fallback 是什么？静默吞掉、报错中止、还是回退原值？规约有没有写？
- "warn and continue"被用在了模式决策上吗？（模式选错是数据损坏级问题，警告后继续等于没修）

## 5. 幂等与重入

- 操作跑两遍结果是否一致？（替换类操作二次执行会不会二次替换/叠加？）
- 中途失败后重跑，会从脏状态继续还是能安全恢复？

## 6. 先例同构性

- 规约声称"照抄先例 X"——X 和本需求真同构吗？核对过数据流向、作用域、触发机制三要素吗？（找错先例照错抄，比不找更糟）
- 第一次找到的先例就是对的吗？有没有第二候选被排除的理由？
- 若是 de-novo 设计（无先例），规约是否显式宣告了？de-novo 应触发更严的审查强度。

## 7. 输入形态枚举

- 用户输入/外部数据的所有合法形态是否被枚举成表？（协议变体、可选后缀、端口、子路径、引号嵌套……）
- 规约只覆盖了 issue 里报的那一种形态，还是全枚举？每修一种形态会不会引入新盲区？

## 8. 入口路径完整性

- 修改的决策/分派逻辑有几个入口路径？规约的改法覆盖了全部入口，还是只覆盖了 grep 到的那一个？
- 有没有 early-return 守卫会让某些 flag 组合绕过修改点？
- 每个入口路径有对应测试吗？测试用的 flag 组合是"命中该路径"的组合还是"恰好绕开"的组合？

## 9. 写入方完整性（schema 变更类）

- 删除/新增字段时，是否枚举了**所有**写入方（creator / hooks / 迁移脚本 / 类型声明 / 跨语言副本）？只改 creator 的"废弃"会被其他写入方悄悄写回。
- 类型声明（TypedDict / interface）也算写入方——读方契约的写入方。

## 10. 完成诚实性

- "完成"的定义写清楚了吗？代码写完 ≠ 完成；验收 + 合并 + 提交都做完才算。
- 规约的交付清单里，哪些是"必须验收通过"项，哪些是"尽力"项？断点如何如实标注？

## 11. 兼容与回滚

- 旧数据/旧版本/未升级环境撞上新逻辑会怎样？有显式兼容策略还是"应该没人在用旧的"？
- 出问题时的回滚路径是什么？改一行配置能放行，还是必须 revert 代码？

## 分层侧重（三层 fusion 打磨）

每层挑刺聚焦不同维度，避免三层重复问同一批问题：

| 层 | 攻击侧重 | 主用维度 |
|---|---|---|
| **prd** | 需求矛盾 / 验收可测 / 范围边界 | 3（验收可靠性）、10（完成诚实性）、目标-手段错位（需求本身是否自洽、范围内/外是否清晰） |
| **design** | 逻辑盲区 / 边界 / 隔离 / parse / 幂等 / 先例同构 | 1（边界误伤）、2（作用域隔离）、4（parse 校验）、5（幂等重入）、6（先例同构）、9（写入方完整性） |
| **implement** | 执行顺序 / 回滚 / 验证充分性 | 8（入口路径完整性）、11（兼容回滚），加执行序依赖、"行为变更 vs 叠加"、现有测试会否翻红 |

- implement 轮**只攻 design 未覆盖的独有项**，且挑刺记录须引用 design 轮发现标注 采纳/反驳/独有（见 `review-record-template.md`）——防复读。

## 用法建议

- 多 reviewer 并行时按组分配：如 rev-a 攻 1/2/6/9，rev-b 攻 3/4/5/7，主会话自查 8/10/11。
- 不是每个维度都适用于每层——不适用的维度在挑刺记录里可以不出现，但**适用却没被攻**的维度是审查漏洞。
