# 实现报告骨架（先例资产）

实现报告是**先例库**的基本单元：下次同类需求出现时，`trellis-pb-find-precedent` 的第一路（仓库内先例）搜的就是这些报告。先例库随任务自增长——每个复杂任务归档前留一份，飞轮才转得起来。

写作立场：**写给下一个照抄的人**，不是写给验收的人。重点不是"我做了什么"，而是"哪些结构可以直接抄、哪些决策为什么这么定"。

## 骨架

```markdown
# Implementation Report: <功能名>

date: <YYYY-MM-DD>
task: <任务目录名>
related: <spec-review.md / design.md 路径，便于回溯决议链>

## 一句话定位

<这个功能是什么、用一句话说明"什么时候该来抄我"。
例："UI 开关触发字符串级公式替换"类需求的先例>

## 改动结构

| 文件 | 改动 | 角色 |
|---|---|---|
| <path> | <新增/修改 N 行> | <这处改动在整体结构中的职责> |

<改动之间的依赖/数据流一两句：谁产生数据、谁消费、开关从哪进从哪出>

## 关键决策

每条：决策 + 为什么 + 排除了什么替代方案。

- <决策 1>：<理由>；排除了 <替代方案>（因为 <原因>）
- …

## 可照抄点

明确列出"结构同构的新需求可以直接复用"的部分：

- <可照抄点 1：如"五文件改动结构"、某个校验-fallback 模式>
- …

## 不可照抄点（同构性边界）

同样重要——**在哪些条件下本先例不适用**，防止下一个人找错先例照错抄：

- <前提条件：如"仅适用于命中段可被 token 边界切分的场景">
- …

## 测试与验收方式

<用了什么确定性断言（snapshot / mock 精确值），照抄时测试结构怎么复用>
```

## 归档位置

放项目的文档惯例位置（如 `docs/reports/`、`docs/modules/`）；项目无惯例时放任务目录内（归档后仍可被全文检索到）。在 `harvest.md` 的 `precedent:` 行记录最终路径。
