# 程序性知识 → skill 提炼

## 判据：什么值得成为 skill

**同类操作出现 ≥2 次才提炼成 skill。** 第一次出现时只在 harvest.md 记一笔（"首次出现，观察中"）；第二次出现说明它是模式不是巧合，此时提炼。

这条判据防的是**过度沉淀**：一次性的操作流程写成 skill 只会稀释 skill 库的信噪比，让真正高频的 skill 更难被发现。skill 库和先例库一样，质量靠克制维持。

补充判据（满足 ≥2 次之后再看）：

- **可复述性**：流程能写成"触发条件 → 步骤 → 验证"吗？依赖大量隐性判断的不适合成 skill，适合留在先例报告里。
- **稳定性**:流程依赖的工具/结构是否稳定？下个月就会变的先别沉淀。
- **通用度**：只对当前任务成立的是先例（precedent），对一类任务成立的才是 skill。

## 提炼骨架

新 skill 文件的最小结构：

```markdown
---
name: <kebab-case 名称>
description: <一句话：什么场景用、产出什么。这是路由表面，写清触发信号>
---

# <名称>

<两三句：这个 skill 解决什么问题、为什么值得存在（引用它诞生的两次案例）>

## 触发条件

- <用户信号 / 任务状态信号，具体到可判断>

## 步骤

1. <可执行的步骤，含命令/文件路径模板>
2. …
n. <验证：怎么确认做对了>

## 反模式

- <这两次案例里踩过或差点踩的坑，每条一行>

## Not For

- <容易误触发但不该用本 skill 的场景>
```

## 提炼纪律

- **从真实案例提炼，不从想象提炼。** 每个步骤和反模式都应能指回具体任务的具体经历。
- 反模式表是 skill 的核心价值——踩过的坑比正确步骤更难从模型先验里恢复。
- skill 成文后 dogfood 一遍：按 skill 自己的步骤走一次，确认 skill 本身"不装"（写的和做的一致）。
- 已有相近 skill 时优先**更新**它（补触发条件/反模式），不另立新 skill 造成路由歧义。
